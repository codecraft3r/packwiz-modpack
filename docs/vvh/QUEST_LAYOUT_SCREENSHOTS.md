# VvH quest-layout screenshot protocol

This is the acceptance procedure for the ten Season One chapter layouts. The PNGs generated by `scripts/vvh_render_layouts.py` are **source-level review boards, not Minecraft or FTB Quests screenshots**. They help find overlaps, long edges, and art collisions before launch. Only captures made in the running client satisfy the visual acceptance check.

## Deterministic source review boards

From the Packwiz repository root, render the current manifest and include the distributed Poiesis art pack when it is locally available:

```powershell
python scripts/vvh_render_layouts.py `
  docs/vvh/campaign_manifest.json `
  docs/vvh/evidence/layout `
  --resource-zip C:\path\to\poiesis-living-atlas-art-v5.zip
```

The renderer writes ten chapter PNGs, `contact_sheet.png`, and `render-metadata.json`. Metadata records the manifest and resource-pack SHA-256 values, identifies the artifact as non-runtime evidence, and lists unresolved namespaced images. Unresolved images appear as labelled placeholders; this is expected unless ZIPs containing vanilla and mod textures are also supplied with repeated `--resource-zip` arguments.

Before visual review, regenerate `docs/vvh/campaign_manifest.json` through the repository's normal build workflow so its coordinates match the candidate SNBT. Do not use an old contact sheet to approve edited chapter files.

Source-board checks for every chapter:

- no quest-node circles overlap;
- labels have enough separation to remain distinguishable;
- dependency lines do not create ambiguous crossings or pass through unrelated nodes;
- the central communal/world-building route reads as the primary spine;
- optional progression and faction routes read as side branches and visibly reconnect or end deliberately;
- chapter artwork does not obscure nodes, labels, dependency junctions, or the spine;
- no asset is silently absent: every placeholder is explained by `unresolved_references` or fixed before release.

## Required in-client capture setup

Use the materialized client for the exact Packwiz revision under test. Record the Packwiz revision, Minecraft version, FTB Quests version, Poiesis ZIP SHA-256, display resolution, GUI scale, language, and resource-pack order in the session note.

Use these fixed settings unless the client cannot support them:

- window/content size: 1920 × 1080;
- GUI scale: 2;
- language: English (US);
- UI/resource packs: release order, with Poiesis enabled;
- quest edit mode: off;
- quest progress: reset or a fresh test team, so completion tint does not hide artwork;
- capture format: lossless PNG, with no post-capture crop, resize, annotation, or color adjustment.

If a different resolution or GUI scale is unavoidable, put it in the filename suffix and session note. Do not mix settings silently in one evidence set.

## Capture sequence and filenames

Create `docs/vvh/evidence/client-layout/<session>/`, where `<session>` is `YYYYMMDD-HHMM-<short-revision>`. Capture in chapter order, without moving nodes or entering edit mode:

1. Open the chapter and use **Fit All** (or the closest FTB Quests fit-to-content control).
2. Wait two seconds for textures and item icons to settle.
3. Capture the entire quest window as `00_vvh_00_island_charter_fit.png` through `09_vvh_09_after_the_bells_fit.png`.
4. Return to the world for at least one frame, reopen the chapter, select the central opener, and capture it at the normal readable zoom as `<nn>_<chapter>_detail.png`.
5. For chapters 02, 03, 04, and 05, pan once from the top of the central spine to the lowest visible shared milestone. If the whole branch is not legible in the detail capture, add `<nn>_<chapter>_branch-a.png`, `branch-b.png`, and so on.

The minimum complete set is 20 PNGs: one fit view and one readable detail view for each chapter. Extra branch captures are required when labels or dependencies cannot be judged at the detail zoom.

## Review rubric

Mark each item pass, fail, or not applicable in a session note named `RESULTS.md` beside the PNGs.

| Area | Pass condition |
|---|---|
| Chapter identity | Title and chapter icon/logo are present, recognizable, and not clipped. |
| Background/art | Intended panorama, crest, and decorative assets load; crop and alpha look deliberate; artwork does not compete with objectives. |
| Icons | Quest icons render without missing-texture tiles and remain recognizable at fit and detail zoom. |
| Central spine | Shared world-building progression is visually central, continuous, and readable from top to bottom. |
| Side branches | Optional faction/progression paths are visibly subordinate, have an obvious origin, and do not look accidentally gated. |
| Dependencies | Lines attach to the intended nodes, avoid confusing crossings, and are visible against the artwork. |
| Labels | Titles do not collide, clip, or become indistinguishable at the detail zoom. |
| State styling | Mandatory versus optional nodes and any minimum-dependency junction remain visually distinguishable. |

Any missing texture, unexpected logo/background, unreadable branch, or ambiguous dependency is a failed visual gate. Record the chapter, screenshot filename, observed problem, and intended correction. Static validation or a dedicated-server parse cannot convert that failure into a pass.

## Evidence status

No in-client screenshots are established by this document or by the renderer. Until a dated `client-layout/<session>/RESULTS.md` and its PNG set exist, normal-scale client rendering, text wrapping, artwork crop/contrast, and final branch readability remain unverified.
